## 分析 111.md（Mosaic 需求与技术方案 V1.0，126 节 / 7478 行）

产出：`D:/project/mosaic/DEVELOPMENT-PLAN.md`

### 项目要点
- Mosaic = AI 原生、自托管家庭影音平台。技术栈：Rust（Axum/Tokio/SQLx）+ Vue3+TS+Tauri2（六端统一）+ FFmpeg + SQLite/PostgreSQL。
- 核心抽象：MediaItem → MediaVersion → MediaFile → MediaStream；StorageProvider / MetadataProvider / HardwareProvider / ModelProvider / MediaPlayer Plugin / AI Agent+Tool+MCP。
- 首发方向：R5S / RK3588S / ARM64 + Docker。明确不做 BT/PT/下载/网盘。

### 分析结论（关键判断）
1. 文档是白皮书不是开发计划：缺字段级数据模型、API 规范、验收标准。
2. 反对按 §114 的 V0.1→V1.0 线性推进，改为垂直切片：P0 地基/Spike → P1 媒体内核 → P2 元数据 → P3 播放引擎（第一个可用版）→ P4 Web+桌面端（对外发布）→ P5 ARM/R5S → P6 移动TV → P7 AI 与生态。3 人约 48 周，1 人建议只做到 P4（约 50 周）。
3. 两个生死级 Spike 必须在 P0 出结论：S1 Tauri2 移动端原生播放器插件（Media3/ExoPlayer，PGS/ASS 字幕、Surface 叠加）；S2 RK3588 硬件转码（mainline FFmpeg 对 RKMPP 支持不完整，通常需 ffmpeg-rockchip，建议做成可切换 runtime 后端 + 自动降级链）。
4. 其他 Spike：S3 FFmpeg 进程池与资源隔离、S4 中文搜索（FTS5 无中文分词 → trigram 起步）、S5 SQLite/PG 双栈、S6 大库扫描基线。
5. 文档 8 处待修订：版本路线与 MVP 口径冲突、缺字段模型、缺 OpenAPI、缺 DoD、RK3588 应为实验特性、字幕降级策略、中文搜索方案、版本号不应写死（改 versions.lock）。

### 关键调整
1. 主目标平台改为 **x86_64 Linux + Docker**；ARM64 构建必须可用；R5S 定位为"最低性能基线设备（Low-end Reference Device）"——只做下限标尺（不崩、Direct Play 流畅、1080p 软转 1 路），不做优化目标。
2. **RKMPP/RGA 移出 1.0**（FFmpeg 主线对 Rockchip MPP 支持不完整，单人最易陷进去的坑）。硬件加速改为 x86 的 QSV / VAAPI / NVENC。
3. **移动端与 TV 整体移出 1.0**，原最大风险项 S1（Tauri 移动端播放器插件）随之消失；P0 的 Spike 改为 Tauri2 + mpv 桌面插件。
4. **AI Agent/MCP、插件系统、PostgreSQL、儿童模式、DLNA、i18n 全部移出 1.0**。
5. 1.0 范围收敛为：Local+SMB 存储、NFO+TMDB 元数据、SQLite+FTS5 trigram、WebSocket 不做、Tauri 插件只做 media-player + storage 两个（原计划九个）。
6. 排期：P0 3 / P1 7 / P2 5 / P3 8（★找用户）/ P4 10（★v0.9）/ P5 5 = **38 周到 v1.0（约 9 个月）**；P6 移动端 +10 周、P7 AI +8 周均为可选、不排期。
7. 新增"一人开发的生存法则"：每月最后一周为巩固周、ADR 必写、P3 结束即对外找 5 个真实用户、遇坑先降级不死磕。

4. `task` 优先级任务队列必须在 P1 就有，否则后面扫描/刮削/转码/AI 全部要返工。
5. 排期：P0 3 / P1 8 / P2 8 / P3 10（★v0.3 找用户）/ P4 14 / P5 8 / P6 12 / P7 18 / P8 11 / P9 14 / P10 8 = **114 周（约 2 年零 2 个月）到 v1.0**。
