**关键决定（后期别改回去）**
- **`decide()` 是纯函数**，不碰 IO/DB/进程 → 兼容性矩阵 100% 离线可测，不必凑真机。
- **降级单向且必须留原因**：DirectPlay → Remux → Transcode → Unsupported，每次降级追加
  带 `code()`/`message()` 的 `Reason`。"不能解释自己的决策等于黑盒"。
- **字幕降级链 Direct → Convert → BurnIn → Drop**，两条硬规则：位图字幕**不做 OCR**；
  **字幕问题永远不能让播放起不来**（任何失败落到 Drop，绝不判 Unsupported）。
- **位图字幕先问客户端能不能自己渲染**（`client.supports(&codec)`），能则 Direct。
  早期版本无条件 BurnIn，导致 mpv 放蓝光原盘也在转码 —— 是兼容性矩阵测试逼出来的。
- **覆盖率按"是否重编码"衡量而非纯 DirectPlay**，且按语料 weight 加权。
  Web 端纯直出率天然只有 22%（浏览器不认 MKV），用 DirectPlay 做跨端指标是自欺欺人。
  这是**换了一个能指导行动的指标，不是悄悄放宽阈值** —— 理由写进 ADR-0001。
- **没有 ffmpeg 返回 501 + `FFMPEG_UNAVAILABLE`，不是 500**。前端据此提示"请安装 ffmpeg"。
- **流式输出目录必须落库**：进程被 kill -9 后没人清理分片，`/cache` 会涨到磁盘满。
  判据是"数据库里登记的目录"，不扫整个 cache（多容器共挂一卷时会误删别人的）。
- ADR：`docs/adr/0001-playback-and-subtitle-degradation.md`。

**测试逼出来的真实缺陷（已修）**
1. ★ 桌面端 Direct Play 只有 69%：位图字幕无条件 BurnIn → 改成先问客户端（修后 97%）。
2. ★ **Windows 内存探测恒为 0**：`wmic` 从 Win11 24H2 起被移除（本机实测不存在）。
   只用它 → 内存 0 → 软件转码并发被压到最低档，**一个不会报错、只会悄悄变慢的退化**。
   改为 PowerShell CIM 优先 + `wmic` 回退，并容忍 PowerShell 开头的空行/横幅。
   修后 `mosaic-cli hardware` 显示 15.7 GB。
3. 语料里 `"audio": "truehd"` 被 serde 静默落进 `Other(String)` 兜底变体
   （`AudioCodec::TrueHd` 的 snake_case 是 `true_hd`）→ 覆盖率悄悄从 97% 掉到 88%。
   已加守卫：加载语料时显式断言 codec 没被识别成 `Other`。
4. P3-6 结束时所有 API 端点**只编译过、从未响应过一次请求** → 补
