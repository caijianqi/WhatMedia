# ADR-0002：前端架构与播放器抽象层

**状态**：已接受
**日期**：2026-10-10
**相关**：ADR-0001（播放决策与字幕降级）、111.md §53（MediaPlayer API）

---

## 背景

P4 要交付 Web + Tauri 桌面两端。两端播放能力差距极大（mpv 能自己渲染 PGS 位图字幕、能直接吃 MKV；浏览器一样都不行），而上层页面不该为这个差异写两套。

111.md §53 已经给出了一个 MediaPlayer 接口草案。本 ADR 记录**沿用它的哪些部分、改了哪些、为什么改**。

---

## 1. 不用组件库（Element Plus）

原计划写的是 `Vue3 + TS + Vite + Tailwind + Element Plus`。**去掉 Element Plus**，只保留 Tailwind + 自写基础组件。

理由：
- 影音 UI 的核心（海报墙、播放器控制条、全屏交互）**没有现成组件可用**，组件库帮不上忙。
- 组件库自带一套企业后台的视觉语言（圆角、间距、主色），在影音场景里要花大量力气覆盖它，最后得到的是"改过的组件库"而不是"自己的设计"。
- 实际需要的可复用组件只有十来个（按钮/卡片/菜单/进度条/开关），自写成本更低、体积可控。

不做的代价：表格、日期选择、复杂表单要自己写。P4 范围内没有这些，出现了再说。

---

## 2. 播放器接口：订阅式，不是轮询式

111.md §53 写的是 `get_position()` / `get_duration()` 这类 getter。**改成 `state` 快照 + `subscribe()`**。

理由：
- 位置每 250ms 变一次。在 Vue 里轮询意味着要么用 `setInterval` 把整个组件树吵醒，要么干脆不更新 UI。
- 底层本来就有事件（`timeupdate`、mpv 的 property change），推模式是顺着的，拉模式是逆着的。
- 快照不可变、每次变更是新对象 → Vue 响应式和 `subscribe` 的比较都能用引用判等，不需要深比较。

`event`（"刚刚发生了什么"）与 `state`（"现在是什么样"）分开保留：只靠 state 无法区分"首次开始播"和"卡顿后恢复"，而这两种情况用户要看到的提示不同。

**与 §53 的另一处差异**：所有方法返回 Promise，即使底层是同步的。桌面端走 IPC 一定是异步的，现在统一成异步，将来换后端不用改调用方签名。

---

## 3. 能力声明：单一真源 + 编译期比对

"客户端能放什么"有两个消费者：
- 服务端 `ClientCapability` → 决定 Direct Play 还是转码
- 前端 UI → 决定显示哪些按钮

两边各写一份必然漂移，而这种漂移**不报错**——只表现为"服务端觉得你能放 PGS，前端却给了个烧录开关"，或者"前端画了音轨菜单，点了没反应"。

所以：
- 单一真源 = `client/src/player/capabilities.json`
- 前端 `import` 它
- `crates/playback/tests/client_capability_parity.rs` 读同一个文件，跟 Rust 预置档逐字段比对

比对用 serde 的输出而不是手写映射表（手写映射表本身也会漂移，那就成了用一份可能错的知识校验另一份）。

### 3.1 一个自己踩到的坑

第一版 parity 测试用 JSON 对象的 **key** 取客户端 id，而前端用 **`id` 字段**建索引。注入 `id` 漂移后测试**全部通过**——正好漏掉它要防的那件事。

修正：测试用 `id` 字段，并额外断言 key 与 id 必须相等。
**教训：写完测试要注入一次错误确认它会红。能通过的测试不算数，能失败的才算。**

## 4. 能力跟着后端走，不跟运行环境走

一个诱人但错误的写法：桌面端（Tauri）就声明 `tauri-mpv` 能力。

后果：服务端按 mpv 档决策成 Direct Play，给出一个 **MKV 地址**；而 mpv 后端还没就绪、实际在用 Web 播放器时，浏览器放不了 MKV。用户看到"本地文件却播不了"，而服务端日志里一切正常。

所以 `capabilitiesFor(backend)` 按**实际后端**取能力。S1（mpv 能否嵌入 Tauri）落地前，`defaultBackend()` 恒为 `web`；`createPlayer({ backend: 'mpv' })` 会明确 warn 后回落，而不是静默假装成功。

这不是保守，是诚实：宣称自己能放 MKV 却用浏览器去放，比一开始就按 web 决策更糟。

## 5. 浏览器 `<video>` 的真实约束（已写进能力声明）

| 约束 | 后果 |
|---|---|
| `audioTracks` API 基本不存在/只读，且已移出标准 | **播放中无法切换音轨**。`canSwitchAudioTrack: false`，前端不画这个菜单 |
| 位图字幕（PGS/DVBSUB）无法渲染 | 服务端必须烧录，见 ADR-0001 |
| 读不了本地文件路径 | `localFile: false` |

"不画按钮"比"画了点不动"好。能力声明里的这些布尔值就是给 UI 用的。

---

## 6. 进度上报：节流 + 关键节点 + sendBeacon

DoD 要求跨端同步误差 < 5s。两头夹：
- 每秒上报 → 两小时的片 7200 次请求，烧服务端和移动端电量
- 只在退出时上报 → 断电/崩溃会丢掉一大段

取法：
- 常规每 10s 一次（`timeupdate` 节流；位置没变不发）
- seek / 暂停 / 停止**立即**发（seek 是跨度最大、最易丢的操作）
- 页面隐藏 / 卸载时 flush，走 `navigator.sendBeacon`——普通 `fetch` 在卸载时大概率发不出去

`flush()` 幂等，所以可以放心在 `pause` 和 `pagehide` 里各调一遍。

---

## 7. hls.js 按需加载

`import('hls.js')` 动态加载，不进主包。实测有效：构建产物里 hls.js 是独立 595KB chunk，主包 98KB。Direct Play 的用户一辈子不会下载它。

加载失败时退回原生 HLS（Safari），都不行才报 `decode` 错误——而不是让整个播放器挂掉。

---

## 8. 详情页只做决策预览

`GET /playback/decide` 无副作用；`POST /playback/sessions` **会启动 ffmpeg 转码任务**。

所以详情页用前者，播放器页才用后者。否则每打开一次详情页就会在服务端留下一路转码——一个不会报错、只会慢慢吃满 CPU 的问题。

---

## 9. 尚未做（及原因）

- **mpv 后端**：等 S1 结论。在此之前不做"假实现"——假实现会让桌面端看起来能用，但播 MKV 时失败，且失败原因难以追溯。
- **OpenAPI 自动生成类型**：当前 `src/api/client.ts` 是手写的，字段与服务端结构体一一对应，文件头已标注。手写必然漂移，接 utoipa 后替换为生成产物。

---

## 10. 后果

- 桌面端在 S1 落地前等价于 Web 端。这是接受了的成本，换来的是不会出现"看起来能用实际不能用"。
- 组件库缺失意味着后续复杂表单要自己写。
- parity 测试把前端 JSON 变成了 Rust 测试的依赖：移动或重命名该文件会让 `cargo test` 失败。这是有意的（硬失败好过静默失效）。
