# Spike S3：FFmpeg 进程池与资源隔离

- 阶段：P0（设计）→ P3（落地）
- 时间盒：**1.5 周**
- 状态：待启动 | 依赖：P1 的 `task` 优先级队列（已就绪）

## 要解决的问题

111.md §107 只写了目标：

> 扫描不影响播放，刮削不影响播放，AI 不影响播放

但没写手段。在家庭小主机（尤其 R5S 这种 4 核 ARM）上，一次全量扫描 + 一千部电影刮削 + 一路转码同时跑，播放必然卡。**这不是调参能解决的，必须有机制。**

## 四层机制

### 1. 优先级队列（已实现）
`crates/task` 的 `TaskQueue` 已实现，四个优先级：

```
Critical  播放相关（用户正在等）
High      转码
Normal    刮削
Low       扫描
```

已有测试守护不变量：`playback_preempts_background_scan`。

### 2. 并发上限与自适应
- 并发度按 CPU 核数自适应，小主机自动降到 1–2
- FFmpeg 进程池：**转码进程数与扫描进程数分开限流**，不共用池
- R5S 上的具体数值由本 Spike 实测给出，写进 `docs/benchmark/`

### 3. OS 层资源限制
- 后台任务进程 `nice` 提升（Unix）
- 可选：cgroup v2 限制扫描/刮削进程的 CPU 配额
- 转码进程的线程数显式限制（`-threads`），避免 FFmpeg 默认吃满所有核

### 4. 播放抢占
播放请求到达时：
- 正在跑的 Low/Normal 任务**可暂停**（不是杀掉），让出 CPU
- 转码任务若为同一媒体则复用，不重复启动
- 播放结束后恢复被暂停的任务

## 产出

1. `TaskQueue` 的 async worker 池实现（P1 完成 queue，本 Spike 完成 worker）
2. R5S 上的并发上限数值表
3. 一个可复现的验证脚本：边跑全量扫描边播放，记录卡顿次数

## 验收标准

> **播放期间触发全量扫描，播放不卡顿。**

量化：1080p Direct Play 期间启动 10,000 文件全量扫描，播放端卡顿次数 = 0。

## 备注

这一条直接支撑 P3 的 DoD 与 R5S 的"最低性能基线设备"定位。如果 R5S 上做不到，说明并发上限还要再降 —— 那就降，不要硬扛。
